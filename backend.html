API & data

The data, grouped

Platform tables are shared by everyone. Store tables carry a tenant_id and are filtered by the database (how). Full ER diagram: storeease-backend/docs/erd.svg.

Platform (shared)

  • tenants: one row per business, its address and status
  • users: one global identity per person
  • platform_admins: the StoreEase team
  • shoppers + shopper_addresses: one person and their address book, for every store
  • email_verification_codes: the owner's 6-digit code
  • plans, MRR snapshots, webhook events, email log

Who works where

  • tenant_memberships: person × business × owner/staff
  • staff_roles + permissions
  • refresh tokens

Store setup & catalogue

  • store_settings: name, theme, colours, logo
  • domain verifications
  • categories, products (stock count lives here), product images

Shoppers & orders

  • customers: the link between a shopper and one store (blocked, notes, first order), login codes
  • orders, order items (address snapshot kept)
  • product ratings
  • return_requests with their items, photos and history; orders also carry the payment method and status

Inventory

  • sales: every stock-taking event (website orders automatically)
  • stock_adjustments: restocks, write-offs, corrections
  • sales channels, add-ons

Billing

  • subscriptions, invoices, payments
  • billing notices (which reminder went out)
  • setup requests

Work that runs on its own

Five loops run inside the API process. One API container means exactly one of each.

✉️

Email sender

Every 5 s. Sends queued order and welcome mail, retries with backoff.

💳

Billing sweep

Every 15 min. Trial reminders, graces, suspensions, monthly renewals in instant mode.

🌐

Domain re-check

Hourly. A verified custom domain whose DNS record vanished stops routing; the owner is emailed.

↩️

Returns sweep

Hourly. One reminder email per store for requests waiting 3 days or refunds unpaid 7 days; 90 days after a request is final it deletes the photos and the bank/UPI details.

📈

MRR snapshot

Daily row per paying store, so platform charts have history.

Emails

Plain text plus simple HTML, from templates in app/emails/templates/. On the server they are sent through Amazon SES (from no-reply@storeease.in); on a laptop they land in Mailpit.

To shoppers

Login code · order confirmation · confirmed · shipped · cancelled by the store · payment received · return or replacement update (one template, every status). Order confirmation says how to pay. From "<store> via StoreEase", replies go to the store.

To owners & staff

Welcome · email verification code · new order (names the payment method) · return requested · reminders on stuck requests · staff invite · password reset/changed · email change · setup progress · suspended/reactivated.

Billing

Trial ending/ended · receipt · payment failed/halted · suspension soon · cancel ending.

Conventions

Thin routes

app/api/v1/x.py is the HTTP contract only; all logic lives in app/services/x.py.

Stock moves one way

Only through app/services/stock.py, so every change lands in the ledger. Oversell is a clean 409 listing every short line.

Long lists use a cursor

Sales and stock ledgers page with "load more", never page numbers, so page 5,000 is as fast as page 1.

Errors carry a code

store_suspended, addon_required, insufficient_access, plan_limit_reached… the UI maps each to a clear screen.

Emails after commit

Links come from settings, never from the request's address (blocks host-header tricks).

Docs in the same PR

A behaviour change updates the endpoint index, the design doc, the ERD and the process diagram together.
