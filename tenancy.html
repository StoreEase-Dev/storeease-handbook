How it is built

Keeping stores apart

One app and one database serve every business. Priya must never see another store's products, orders or customers: not through the API, not through a bug, not through a crafted request. This page shows how.

The choice: shared tables, filtered by the database

Not chosen

A database per store

Hundreds of databases to migrate, back up and monitor. Too expensive for ₹499 customers.

Not chosen

A schema per store

Every migration runs once per store. Still heavy at our scale.

Chosen

Shared tables + tenant_id + RLS

Every row says which store it belongs to. PostgreSQL itself hides other stores' rows on every query.

One request, start to finish

A shopper opens Priya's catalogue.

The client never sends a store id

It comes from the address (or the signed login token). A forged field is ignored.

Even buggy code is safe

If a query forgets the filter, or trusts a wrong id, the database still returns nothing from other stores.

Proven by tests

The isolation suite attacks one store with another's ids at database and HTTP level, and fails if any table lacks a policy.

Three database roles

None of them is a superuser. The app's main role owns nothing, so the safety rules always apply to it.

RoleUsed byCan do
storeease_migratorMigrations, at deploy timeOwns the tables. Changes the schema. Never serves a request
storeease_appEvery store and shopper requestReads and writes, always filtered to one store (or, for shopper rows, to the signed-in shopper)
storeease_adminAdmin portal, login, billing, background jobsSees every store. Code using it must filter by store itself; tests check which modules may use it

Rule for developers: a new table that holds store data gets its tenant_id and its policy in the same migration, never later.

Tokens never touch storage

The short token lives only in the page's memory. The renewal token is a locked-down cookie that scripts can't read. A reused renewal token kills the whole session family.

Owners and staff never mix

An account is either owner-type (may own several businesses) or staff-type (may work at several). A staff member wanting their own shop signs up with another email.

The hand-over from login to store

Staff log in on one shared address but work on their store's address. Cookies can't cross addresses, so a one-time token does.

Shoppers belong to StoreEase, not to one store

One person, one account, many shops. A shop only ever learns about the people who ordered from it.

A second safety tag

Shopper rows have no store id, so the database keys them to the signed-in shopper instead. A staff session never carries that tag and sees no address book. The isolation tests cover it.

Shared, with limits

Name, phone and addresses are shared. Old orders keep their own copy of the address. Ratings and analytics stay per shop.

Shoppers are told

Login and the account page say their details are saved with StoreEase for any StoreEase shop.

Email verification gate

A new owner must confirm their email with a 6-digit code (valid 10 minutes, 5 tries, resend once a minute). Owners who signed up before this existed count as verified.

locked until verified
  • Store settings and logo
  • Products, categories, images, CSV import
  • Publishing
  • Buying a plan or add-on
still open
  • Looking at anything
  • Unpublishing and cancelling

The API answers a locked request with 403 email_not_verified before it does anything; the dashboard only greys out the buttons to match. The same applies to staff invited by link (setting a password verifies them) and to a confirmed email change.

Store status gates

unpublished

New stores. The shop shows a playful "coming soon" page; the dashboard works. Publishing needs a paid plan and a verified email.

suspended

By an admin or by billing. Shop shows a playful "temporarily closed" page, staff signed out, the owner can still sign in, see why, and pay.

deleted

Soft delete: a playful "no such shop" page everywhere, data kept, address reserved, restorable by an admin.
