Running it

Deploy & operate

Deploys are one button in GitHub with a checkbox per service. Day-to-day work on the server goes through AWS Session Manager. There is no SSH.

The deploy robot (GitHub Actions)

Not an AI: a robot that follows a fixed recipe, storeease-infra/.github/workflows/deploy.yml.

🖥️

Borrows a fresh computer

Each run gets a clean machine from GitHub for a few minutes. Nothing runs on anyone's laptop.

📜

Follows the recipe

Download the code, build, test, upload. The same steps every time.

🪪

Shows an ID to AWS

No AWS password in GitHub. AWS checks a signed ID from GitHub and hands out a key that expires in an hour (OIDC).

What's on the server

EC2 t3.micro (1 GB RAM + 2 GB swap), Amazon Linux 2023, everything in /opt/storeease under Docker Compose.

nginx

HTTPS for origin.storeease.in (Let's Encrypt, renews itself). Refuses anything without CloudFront's secret.

api

The backend image, settings written from SSM into api.env at each deploy.

postgres

PostgreSQL 17 on the server's disk. Nightly backup to S3 at 02:00 IST, kept 14 days.

mailpit

Only a safety net now: the API sends through Amazon SES, so nothing arrives here unless mail.mode is set to mailpit.

Everyday tasks

Install the AWS CLI and the Session Manager plugin first. Server commands need sudo.

Open a shell on the server

aws ssm get-parameter --name /storeease/dev/infra/backend_instance_id --query Parameter.Value --output text
aws ssm start-session --target <instance-id>
cd /opt/storeease

Logs

sudo docker compose logs --tail=200 -f api
sudo docker compose logs --tail=100 nginx postgres mailpit
sudo docker compose ps

Read the emails (Mailpit)

aws ssm start-session --target <instance-id> --document-name AWS-StartPortForwardingSession --parameters '{"portNumber":["8025"],"localPortNumber":["8025"]}'

Keep the window open, then visit http://localhost:8025.

Database (psql)

aws ssm start-session --target <instance-id> --document-name AWS-StartPortForwardingSession --parameters '{"portNumber":["5432"],"localPortNumber":["15432"]}'
psql -h 127.0.0.1 -p 15432 -U postgres -d storeease

Password: SSM /storeease/dev/backend/POSTGRES_PASSWORD.

Create a platform admin

sudo docker compose exec api python -m app.cli.admin create --email you@example.com --name "Your Name"

Backups

sudo /opt/storeease/bin/backup-db.sh            # one now
sudo bin/restore-db.sh backups/db/storeease-<time>.sql.gz   # replaces live DB

Email (Amazon SES)

Outgoing mail (login codes, orders, billing) goes through SES. Incoming mail to info@storeease.in stays in the GoDaddy mailbox. Decision D-SES1.

RecordWhereWhy
DKIM: 3 CNAMEs <token>._domainkeyrootSES signs each mail; receivers check the signature. Terraform creates and validates them
SPF: one TXTrootGoDaddy's only. Never add SES here: two SPF records break both
MAIL FROM: MX + SPF TXTmail.storeease.inSES's own bounce address. This is where SES's SPF lives, so the root keeps one
DMARC: one TXT _dmarcrootGoDaddy's record, kept as it is (p=reject). SES mail passes through DKIM alignment. Edit it in project.yaml, never add a second
Mailbox: MX, DKIM CNAMEs, autodiscoverrootNeeded for info@ to receive. They vanished when the nameservers moved and are now domain.extra_records in project.yaml
1 · once

Re-run bootstrap/

Lets the Terraform role manage SES. Without it the apply fails with AccessDenied.

2 · you ask AWS

Production access

Console, Mumbai region, SES → Account dashboard. Until AWS agrees (about a day), SES mails only verified addresses.

3 · deploy twice

Apply, then Backend

Terraform apply first, then Deploy Backend (rewrites api.env). Click the confirmation link in the "Subscription Confirmation" email, or bounce notices never arrive.

Test itSign up with a real Gmail address. In the code mail choose ⋮ → Show original: SPF, DKIM (domain storeease.in) and DMARC must all say PASS. Bounces and complaints go to an SNS topic that emails the ops address; nothing in the app reads it yet.

Security headers and framing

Who may frame whomThe dashboard shows the shop in a preview frame on the same address, so only the app distribution sends frame-ancestors 'self' and X-Frame-Options: SAMEORIGIN. The homepage and the uploads site stay at "nobody may frame". Every shop is its own address, so one shop still cannot frame another, and outside sites cannot frame anything. The same policy lists the uploads bucket's own S3 address, because browsers upload photos straight to it. Decision D-AWS7.
